Section kinds for C (use only the kinds listed here):
- `## VariableDef <Name>` for every file-scope variable (`static` ones included; `extern` declarations excluded) and every `#define` macro (object-like and function-like; include guards excluded).
- `## ClassDef <Name>` for every `struct`, `union` and `enum` definition with a body and every `typedef` (`typedef struct tag {...} T;` is one section named `T`).
- `## FunctionDef <Name>` for every function definition, `static` functions and `main` included. Function prototypes are not sections.
- The first line under every header is `**<Name>**: <one-sentence summary>.` This line is used as the symbol summary in a wiki, so make it a real summary.

## Rules

1. Document EVERY top-level declaration of the file, public and private, in the SAME ORDER as in the source. The request lists the sections required; use exactly those headers. Do not rename, skip, or invent sections.
2. Types: give the exact definition in a fenced `c` block: the struct/union/enum tag, every member with its exact name, type, array size and bit-field width, every enumerator with its explicit value, and the typedef name. Comments may be dropped. Then explain member semantics, invariants and ownership of pointer members in prose.
3. Variables and macros: give the exact definition in a fenced `c` block, including storage class (`static`, `const`), type, array size and initializer, and for macros the exact `#define` line with its parameters and replacement text. If an initializer is longer than about 20 lines (large tables), describe its content precisely in prose instead.
4. Functions and methods: give the exact signature in `**Signature**:`. Then describe, in natural language:
   - the behavior and the observable order of operations;
   - edge cases and boundary conditions (empty, zero, negative, missing keys; `<` versus `<=`);
   - the exact signature including storage class (`static`, `inline`), `const` qualifiers, pointer levels and parameter names;
   - error reporting: return codes, `errno`, out-parameters (when they are written and when they are left untouched), NULL returns;
   - memory ownership: who allocates and who frees each pointer argument and return value, buffer sizes and termination (`'\0'`), truncation rules;
   - side effects: file-scope and global variables read or mutated, output written with `printf`/`fprintf` (exact format strings), files, signals, `exit`/`abort` calls;
   - which other functions, methods and types of the project or of imported libraries it relies on;
   - the exact return values, including exact output strings and number formats.
5. Put exact literals (strings, format strings, numbers, field names, dictionary keys, header names, environment variable names) inline in backticks. Exact values matter: tests compare them.
6. Do NOT write function or method bodies, pseudocode, or line-by-line transcriptions, and no fenced code blocks for functions or methods. Describe behavior and contracts precisely enough that an expert C programmer reproduces the same observable behavior.
7. Declarations listed in the context come from the repository headers this file includes or from OTHER source files of the same directory unit: do not document them as sections of this file, but name them when this file uses them; name the struct members and macros of such declarations that this file uses exactly, in backticks.
